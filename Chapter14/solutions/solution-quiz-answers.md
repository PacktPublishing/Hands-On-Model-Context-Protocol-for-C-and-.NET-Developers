# Chapter 14 — Quiz answers

1. Convert the Dockerfile to a multi-stage build. Restore and publish in a `mcr.microsoft.com/dotnet/sdk` build stage, then copy only the published output into a clean `mcr.microsoft.com/dotnet/aspnet` runtime stage and run it as the built-in non-root `app` user. The compiler, CLI tools, package caches, and their vulnerable transitive components remain in the discarded build stage. The final image becomes much smaller because it contains only the ASP.NET Core runtime and published application binaries rather than the full SDK and source tree.

2. A minimum replica count of 0 lets Container Apps scale the service to zero during quiet periods. The next request must allocate a replica, start the container, and initialize .NET and the application, causing the intermittent cold-start delay. Set the minimum replica count to 1 for consistently low latency, and tune the remaining KEDA rules for burst scaling. This removes scale-to-zero savings because one replica now runs continuously; the team must compare that baseline compute cost with the user-facing latency budget.

3. Adding a new tool without changing existing contracts is a backward-compatible capability addition, so the library receives a minor version increment. The cancellation and refund are separate side effects, and a failure between them can leave a canceled booking without a completed refund. Durable Functions is appropriate when the operation needs persisted checkpoints, retry-safe activities, and compensation or recovery across restarts. Each activity must be idempotent because Durable Functions provides at-least-once execution.

4. Any branch, including an unreviewed or compromised feature branch, can exchange its GitHub OIDC token for Azure credentials and deploy arbitrary code to production. Restrict the federated credential's subject to the protected production source, such as the exact `main` branch or, preferably, a protected GitHub production environment. Require environment approvals and branch protection so only reviewed commits can reach the production deployment job.

5. Immediately set the new revision's traffic weight to 0 and return all traffic to the healthy previous revision; do not continue the canary or promote it. Use revision logs, health probes, Container Apps events, dependency telemetry, and correlation IDs from the failed requests to determine whether startup, configuration, secret, network, capacity, or downstream dependency failures caused the 503s. Correct the cause and verify the image in a non-production environment. Attempt a second canary only after automated tests and probes pass, configuration and migrations are compatible, and a representative soak period meets the defined error-rate and latency thresholds with no unexplained 503s.
