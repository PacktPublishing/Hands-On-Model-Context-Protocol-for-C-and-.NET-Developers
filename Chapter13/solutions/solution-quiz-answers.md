# Chapter 13 — Quiz answers

1. A 403 means token authentication succeeded but authorization failed. First, the token may lack the `travel.payments.process` scope; decode the token, inspect its `scp` claims, and verify that the client requested and was granted that scope. Second, the server's `ToolScopeMap` or authorization policy may map `process_payment` to a different scope; inspect the deployed mapping and authorization logs, then compare the required scope with the token. Signature, issuer, audience, and expiry failures would normally produce 401 rather than 403.

2. Each replica is probably using its own local ASP.NET Core Data Protection key ring. A login cookie encrypted by replica A cannot be decrypted when the next request reaches replica B, so B treats the cookie as invalid. Persist a shared key ring in Azure Blob Storage, protect it with a Key Vault key, and configure the same `SetApplicationName` value on every replica. All replicas can then decrypt cookies issued by any other replica.

3. `HasCapability` cannot find `cancel_flight` in `ToolScopeMap`, returns `false`, and the authenticated client receives 403 without the tool handler running. Denying an unknown tool is the correct fail-closed default: adding a capability cannot accidentally expose it before the team explicitly chooses, documents, and tests its required scope.

4. The application may still have the old key cached when the downstream airline service stops accepting it, causing an immediate outage until configuration refreshes and clients adopt the new key. Detect it through health checks, downstream 401/403 responses, and correlated application logs showing authentication failures after revocation. Recover by temporarily re-enabling the old key or allowing both keys, force or wait for the Key Vault configuration refresh, verify through a real health or test request that the new key is active, and only then revoke the old key again.

5. One hypothesis is an expired token or missing payment scope after a client deployment; first split the APIM 4xx count by status code and inspect JWT validation and scope-policy failures. A second is a Payments-specific APIM policy or rate-limit change; first compare the current policy revision and rate-limit counters with the last known good revision. A third is malformed payment requests or new validation failures in the backend; first follow representative correlation IDs into Payments server traces and group failures by route, validation message, and client version. Keeping the investigations distinct separates identity, gateway, and application causes.

6. Update `TenantContext` to resolve the tenant from a configured claim name or from an explicit allow-list such as `tid` followed by `tenant_id`, while still throwing when neither claim exists or when the values are ambiguous. Do not accept a tenant ID from tool arguments. Add an integration test with two principals using `tenant_id`: seed records for both tenants, query through each principal, and assert that each sees only its own records. Also test that a token with no supported tenant claim is rejected, preserving fail-closed behavior.
