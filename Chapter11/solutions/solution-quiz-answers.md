# Chapter 11 — Quiz answers

1. Recording at the `McpClient` layer captures every tool call the agent actually sends over the protocol boundary, regardless of which internal code path in `RunAsync` triggered it — including calls made by nested helpers, retries, or SDK-level machinery the agent author didn't explicitly log. Logging inside `RunAsync` only sees calls the developer remembered to instrument, and it duplicates logic across every agent. A recorder at the `McpClient` layer would fail to capture a tool call made through a *different* client instance — for example, if the agent (or a sub-agent it hands off to) constructs its own `McpClient` connected to a separate server rather than using the shared, wrapped client the harness recorded.

2. Returning `IsError: true` in the `CallToolResponse` delivers a normal, successful JSON-RPC response whose payload signals a tool-level failure; `McpClient` returns this to the agent as a regular `CallToolResponse` that the agent's own logic must inspect and branch on. Throwing `McpException` instead surfaces as a protocol-level error that `McpClient` translates into a thrown exception on the calling side, unwinding the agent's call stack unless it's wrapped in a try/catch. Use `IsError: true` to simulate expected, recoverable business failures (e.g., "flight sold out", "duplicate booking") that a well-behaved agent should handle gracefully; use `McpException` to simulate unexpected transport/server failures (e.g., server crash, malformed request) that should exercise the agent's exception-handling and escalation path.

3. Add a normalization step that strips or masks volatile, high-entropy tokens — such as booking references, timestamps, and GUIDs — from both the baseline and the current output before computing TF-IDF vectors, typically via a regex substitution (e.g., replace `REF-\d{8}-\d{3}` with a fixed placeholder like `REF-XXXX`). This keeps the similarity score focused on the stable wording and structure of the response instead of penalizing it for a value that is expected to change on every run.

4. Rather than matching hard-coded phrases, `ClassifyBehavior` should classify based on structured signals the agent already exposes: check `AgentResult.RequiresEscalation` first (escalation), then check whether the recorded tool-call sequence is empty or contains only a clarifying "ask" step with no booking/search tool invoked (clarification), and only classify as a completed booking when the expected terminal tool (e.g., `book_flight`) appears in the recorded sequence and returned a successful result. Driving the classification off `RequiresEscalation` and the `ToolCallRecorder` sequence — rather than scanning the natural-language output for marker phrases — keeps the test robust when the LLM paraphrases its response.

5. Add an `AlternativeSequences` property (an `IReadOnlyList<string[]>`) to `GoldenTestCase` alongside the primary `ExpectedToolSequence`, and update the harness's comparison logic to pass the test if the actual recorded sequence matches the primary sequence *or* any entry in `AlternativeSequences`. This lets you record both the old and the new correct tool-call orderings as equally valid outcomes, so a model update that shifts planning behavior without breaking correctness no longer fails the golden test.
